# Memory Management Audit — 2026-11-27

**Scope:** All three processes of Querithm (`v0.1.7`, repo `dev` HEAD `17074b1`, live installed build `0.1.7` contract `1.21.0`, local Release build contract `1.22.0`) — React 19 WebView (`src/`), .NET 10 Sidecar (`sidecar/`), and Tauri v2 Rust shell (`src-tauri/`). Evaluated against `CLAUDE.md` and `docs/ARCHITECTURE.md` (§2, §4, §5, §12, §13, §14).

**Method:**
1. **Live runtime profiling (read-only)** of the active `/usr/bin/querithm` Linux desktop session across two timepoints (~25 min and ~52 min uptime) via `/proc/<pid>/smaps_rollup`, `/proc/<pid>/smaps`, `/proc/<pid>/status`, and `/proc/<pid>/task`.
2. **Controlled isolated Sidecar benchmarks (OS + Managed GC telemetry)** using `/usr/bin/querithm-sidecar` (compressed single-file Release), `sidecar/Querithm.Host/bin/Release/net10.0/querithm-sidecar` (uncompressed Release), `DOTNET_GCConserveMemory=9` A/B comparison, and a non-invasive `DOTNET_STARTUP_HOOKS` probe sampling `GC.GetGCMemoryInfo()` (`Gen0`, `Gen1`, `Gen2`, `LOH`, `POH`, `FragmentedBytes`, `TotalCommittedBytes`) alongside `/proc/<pid>/smaps_rollup` across S1–S4 (both natural GC and forced compacting GC).
3. **Controlled Headless Chrome + Release Sidecar WebView benchmarks** (`--enable-precise-memory-info --js-flags=--expose-gc` + CDP `HeapProfiler.collectGarbage` + `Performance.getMetrics`) against `dist/` + `scripts/dev-bridge.mjs` across S1–S5, **including post-close tab/result/chart recovery checks**.
4. **Full three-layer static & lifecycle source audit** covering `src/`, `sidecar/`, `src-tauri/`, and `scripts/`, with line-by-line verification of every citation and architecture-boundary check (`CLAUDE.md` §1–§4).

No production code was modified during this audit.

**Evidence labels used below:**
- **Measured** — directly observed in live `/proc` telemetry, Sidecar OS + `GCMemoryInfo` S1–S4 runs, single-file A/B test, or Headless Chrome S1–S5 + post-close recovery runs.
- **Read** — traced end to end in source code; defect follows directly from data structures, missing bounds, or missing disposal.

## 1. Executive Summary & Memory Budget Breakdown

Users observing **~700 MB total RAM** during moderate Querithm usage are seeing the combined effect of four compounding causes across all three processes — confirmed by live telemetry of an active Querithm desktop session (**643.4 MiB / 675 MB combined PSS** at 25 min, **639.7 MiB PSS / 915.5 MiB naive RSS** at 52 min):

1. **WebKitGTK Renderer (`WebKitWebProcess`) — 335.8 MiB PSS (52.2% of total PSS):**
   - Starts heavy from a **4.57 MiB eager startup JS payload** (`index-*.js` 2.30 MiB + `monaco-*.js` 2.27 MiB) plus WebKitGTK/JSC/Mesa libraries, then climbs rapidly under query/UI usage because:
     - There is **no global Arrow byte cap across tabs** (`KEEP_EXECUTIONS = 3` × N tabs, **H1**) or across notebook cells (up to 2,000 live `ExecutionData`s + unvirtualized grids/workers, **H2**).
     - **Every incoming Arrow IPC frame is `.slice()`-copied** due to a 3-byte unaligned envelope header (and a 4-byte dev-bridge prefix, **M1**), and `tableToIPC` buffers are `.slice()`-copied again on chart/export serialization (**M15**).
     - Mounted `<ChartView>`s keep dedicated Web Workers + duplicated column copies alive indefinitely even after streaming ends (**H6**).
     - Multiple stores and client caches (`useExplorer.details`, `useDiag.traces`/`debugs`, `useUsages.byTab`, `rowCounts`, `lexer.ts` 4-slot `TokenStream` cache, `providers.ts` `tier2Cache`, and duplicate full `sql` + raw XML/JSON `plans` in `useExecutions`, **H7**, **M4**, **M15**) retain multi-MB state after close or disconnect.
2. **.NET 10 Sidecar (`querithm-sidecar`) — 173.2–177.7 MiB PSS live (27% of total PSS); measured up to 1,184.7 MiB peak / 1,094.5 MiB retained after close under S3–S4 churn:**
   - **Idle/startup inflation (~60–90 MiB):** `<EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>` forces CoreCLR to decompress assemblies into private anonymous `/dev/zero (deleted)` RAM (**+27.2 MiB cold idle, +34.1–35.2 MiB active**, proven via A/B test, **H3**); `RpcServer.cs:67-82` eagerly JIT-warms **all 6 engines** (including `ScriptDom`) on the very first connection regardless of engine used, driving **39.1 MiB** of W^X double-mapped JIT code (`/memfd:doublemapper`) and permanently caching `"__warmup"`.
   - **Managed GC vs Native breakdown (newly measured via `GCMemoryInfo`):** S3 completion/diagnostics churn allocates **276.8 MiB directly onto the LOH** + **64.6 MiB in Gen2** (`360.9 MiB` GC committed vs only `5.7 MiB` unmanaged `[anon]`). When tabs close, `lang.forget` removes dictionary entries without allocating, triggering **zero GCs** — leaving **305–361 MiB of dead LOH/Gen2 resident**! Worse, closing 29 tabs sequentially triggers `onDidChangeModel` → `scheduleDiagnostics` on each intermediate tab (**M15**), spiking Sidecar PSS from **290.2 → 442.1 MiB (+151.9 MiB)** during tab close. Starting S4 Arrow queries on top of uncollected S3 LOH causes Workstation GC (`ConserveMemory=0`) to expand committed segments to **1,094.5 MiB** and never decommit them (`DOTNET_GCConserveMemory=9` slashes that post-close footprint by **-877.8 MiB / -80%**, **C1**). Even after an explicit compacting Gen2+LOH GC post-`lang.forget`, **43.5 MiB (`34.2 MiB` LOH + `9.3 MiB` Gen2)** remains live due to static cache retention (`ChunkedDiagnostics.Cache` string keys, `TSqlParsing.ByHash` edit-orphans, `"__warmup"`, `SchemaCache._snapshots`, **C2**, **H9**).
   - **Provider & feature spikes:** `RefactorService` loads *all* database module definitions from SQLite onto the LOH at once before word-filtering (**M12**), SMO `ServerConnection` leaks event delegates onto pooled `SqlConnection`s and ODP.NET leaves `SelfTuning=true` (**M13**), `MonitorScheduler` leaks a timer CTS per tick while `TextStore._lastBySession` retains raw untruncated & unredacted SQL (**H10**), and DuckDB allows `TotalRAM / 4` *per instance* (**H12**).
3. **Tauri Rust + GTK UI Process (`querithm`) — 118.0 MiB PSS / 222.5 MiB RSS (18.3% of total PSS):**
   - While Rust stays thin in logic, **47 glibc 64 MiB per-thread arenas account for 37.44 MiB (87.6%) of its `[anon]` Private_Dirty** (plus 34.46 MiB in `[heap]` = **71.9 MiB** glibc allocator footprint, **H4**), driven by 38 threads (8 default Tokio workers + 3 sidecar + 12 Mesa/LLVM), cross-thread alloc/free of multi-MB Arrow/JSON-RPC buffers, and glibc's dynamic `M_MMAP_THRESHOLD`.
   - In Rust code: `sidecar.rs:Process::call` holds owned `msg: serde_json::Value` (including multi-MB SQL scripts) inside its suspended `Future` across `rx.await` for the entire RPC roundtrip (**M14**), `on_line` deep-clones `Value` subtrees (**H14**), `ipc.rs` lacks byte caps and an idle sweep timer (**H13**), `updater.rs` pins 50–150+ MiB installers in RAM (**H15**), and `shell_log.rs` clones/allocates per secret before truncating (**M10**).
4. **WebKitGTK Network Process (`WebKitNetworkProcess`) — 16.4–16.8 MiB PSS / 50.8–52.0 MiB RSS (2.5% of total PSS):** Mostly shared `libwebkit2gtk` + `libjavascriptcoregtk` text pages (only 1.85 MiB private anon/heap), running under default `WEBKIT_CACHE_MODEL_WEB_BROWSER` (**M11**).

### Reality Check on `docs/ARCHITECTURE.md` §14 Metric #2 (`≤ 180 MB` Idle RSS)

- **Why naive RSS double-counts on Linux (and in `scripts/bench/run.mjs:1592`):** `libLLVM.so.21.1` (43.4 MiB RSS), `libwebkit2gtk-4.1.so` (56.7 MiB RSS), `libjavascriptcoregtk-4.1.so` (23.1 MiB RSS), and `libgallium` (15.7 MiB RSS) are mapped simultaneously into `querithm`, `WebKitWebProcess`, and `WebKitNetworkProcess`. Summing `ps -o rss=` counts ~125+ MiB of shared clean library text 2–3 times (**897.7 MiB naive RSS vs 643.4 MiB true PSS**).
- **Achievable target after remediation:** WebKitGTK + Mesa/LLVM + .NET 10 cold idle carries an irreducible OS/runtime floor of **~135–165 MiB Combined PSS** (Tauri+GTK ~45–55 MiB PSS + `WebKitWebProcess` ~45–55 MiB PSS + `WebKitNetworkProcess` ~10–12 MiB PSS + uncompressed .NET sidecar ~35–45 MiB PSS). Meeting **≤ 180 MiB Combined Idle PSS** (and ≤ 220–260 MiB post-close steady-state PSS after heavy usage) is realistic once Phase 0–1 fixes land; §14 Metric #2 should gate on **Combined PSS** (Linux) / **Private Working Set** (Windows) alongside per-process RSS.

**Four Proven Root-Cause Insights from §2.3 & §2.3b (Measured):**
1. **LOH dominates S3 intelligence memory (`276.8 MiB` LOH vs `64.6 MiB` Gen2):** Large SQL strings (> 85 KB UTF-16 from JSON-RPC deserialization and `ChunkedDiagnostics.Wrap`) and resized `List<PgToken>`/`List<OracleToken>` backing arrays land directly on the **LOH**.
2. **`lang.forget` triggers zero GCs:** Closing 31 tabs leaves **100% of the 305–361 MiB managed heap resident** (`gcCounts` `462/183/44` unchanged) until subsequent allocations trigger a Gen2/LOH collection — and if S4 Arrow LOH allocations start while 360+ MiB of dead S3 LOH is still uncollected, Workstation GC (`ConserveMemory=0`) expands its LOH segments past **1.09 GiB** instead of collecting!
3. **43.5 MiB (`34.2 MiB` LOH + `9.3 MiB` Gen2) is genuinely leaked past `lang.forget` + full LOH compaction (`S3d`):** Rooted in `ChunkedDiagnostics.Cache` (retaining full wrapped SQL chunk strings as keys), `TSqlParsing.ByHash` (retaining 15 orphaned historical edits of `"doc-edit-churn"`), `"__warmup"`, and `SchemaCache._snapshots`.
4. **DuckDB native memory (`89.0 MiB` in S4a) releases promptly on `session.close` (`→ 26.5 MiB`, `-62.5 MiB`):** Unmanaged memory is only unbounded *while multiple DuckDB instances stay open simultaneously* (`MemoryLimitBytes = TotalRAM / 4` per instance, **H12**).

## 4. Deep-Dive Analysis by Layer & Areas Verified Clean

### 4.1 WebView / Frontend (`src/`)
- **Why `WebKitWebProcess` reaches 335.8 MiB PSS / 438.7 MiB RSS in real usage:**
  1. **Startup floor:** `dist/index.html` eagerly loads `index-CaeQY7FD.js` (2.30 MiB) + `monaco-CAJTagz1.js` (2.27 MiB) + `arrow-tlOdg7NX.js` (168 KiB) + 262 KiB CSS because `src/editor/monaco.ts:2` imports all of `edcore.main`, which misses `vite.config.ts:19`'s `manualChunks` key (`monaco-editor/esm/vs/editor/editor.api`).
  2. **Result & string retention:** Each Arrow `RecordBatch` is `.slice()`-copied on arrival (`frames.ts:30, 75` due to unaligned headers) and retained for 3 runs per tab (`actions.ts:33`) with no global byte budget — plus unlimited cells in notebooks (`runtime.ts:254-262`), while `useExecutions` duplicates full `sql` and raw plan XML/JSON strings (`executions.ts:20-21`).

- **Verified Clean (no false positives):**

  - Only `editor.worker` (226 KiB) is bundled — no TS/CSS/HTML/JSON Monaco workers.
  - `removeTab` (`actions.ts:265-280`) disposes tab executions, calls `query.close`, and disposes models & notebooks (verified in Run C: each closed `200k × 20` tab released ~32.3 MiB of its ~32.5 MiB Arrow data).

### 4.2 .NET 10 Sidecar (`sidecar/`)
- **Why `querithm-sidecar` hits 173.2 MiB PSS live and 1,094.5 MiB after S3–S4 churn:**
  1. **Single-file compression + eager 6-engine JIT:** Cold idle starts at 57.3 MiB PSS (27.2 MiB `/dev/zero` + 13.5 MiB `/memfd:doublemapper`). Opening a single SQLite session triggers `RpcServer.cs:67-82` across all 6 providers (+50.6 MiB immediately).

  - Driver-level pooling is disabled (`Pooling = false`) on all 5 server/file drivers; Core `Pool` enforces `MaxPerProfile = 8` + 5-min idle sweep; `NpgsqlDataSource` cache is LRU-bounded to 64 and retired on `ForgetConnections`.

### 4.3 Rust Tauri Shell (`src-tauri/`)
- **Why `/usr/bin/querithm` hits 118.0 MiB PSS / 222.5 MiB RSS:**
